## Executive summary

The `ares` agent framework's evolution system rests on one observation: any
self-improving system is, at bottom, a loop of **mutation + selection +
inheritance**. The only differences are the granularity of mutation and the
shape of the fitness function.

Two evolution paths fork off a shared `EvolutionScheduler`:

| Path | Token cost | Evaluation | Parents | Output | Use case |
|------|-----------|------------|---------|--------|----------|
| **DreamCycle** | LLM calls (Arena regression) | Quick Reject (5 turns) → Full Eval (50 turns, Welch's t-test) | single-parent mutation | 1 candidate vs baseline | careful re-evaluation of revised editions |
| **Genome GA** | zero tokens, CPU only | based on historical `Score` field | two-parent crossover | whole generation (20) | high-frequency low-cost parameter exploration |

Both paths share the same Scheduler and `StrategyStore`; they diverge only at
the "how to produce and evaluate new strategies" step.

### Key design trade-offs

- **Two paths vs one**: maintaining both adds adapter/config complexity but
  buys separation of cost (token-heavy evaluation) from quality (zero-token
  parameter search).
- **Conservative threshold 0.55**: prefer fewer evolutions over regressions.
  Combined with `p < 0.05` statistical significance, this yields ~30% passing
  Quick Reject and ~10% passing Full Eval — loose initial screen, strict final
  gate.
- **Population size 20**: an empirical GA sweet spot — `<10` suffers genetic
  drift, `>50` is compute-heavy and slow to converge. 20 × 60% survival keeps
  12 individuals per generation with 8 new offspring.
- **Experience-driven evolution**: a pipeline
  `ToolCallRecord → RawExperience → NormalizedExperience → MemoryExperienceStore
  → AggregateEvidence → EvolutionHint` feeds the GA's mutator operator with
  observed failure patterns so mutation is biased toward known-effective
  directions rather than pure random search.

### Runtime component genomes

The GA extends from strategy-parameter evolution to runtime-component parameter
self-tuning via two genomes:

- **`MemoryGenome`** (`internal/evolution/genome/memory_genome.go`) tunes memory
  parameters: `MaxHistory [3,50]`, `MaxSessions [20,500]`,
  `MaxDistilledTasks [500,20000]`, `UseStructuredCleaning`.
- **`PlannerGenome`** (`internal/evolution/genome/planner_genome.go`) tunes
  planning parameters: `Strategy` ("balanced"/"architecture-first"/
  "memory-first"), `MaxSources [3,30]`, `MinRelevance [0.1,0.9]`.

A `MemoryPatcher` (`internal/ares_memory/memory_patcher.go`) implements
`patch.RuntimeComponent` with `Snapshot()`/`Apply()`/`CanApply()` to deploy
GA-evolved parameters at runtime, supporting three patch types:
`PatchChangePlanner`, `PatchChangeBudget`, `PatchChangeReducer`.

This closes the last gap — runtime parameters no longer require manual tuning;
both strategy and memory/planner config evolve within a single
`RunIdleEvolution()` loop.

### Service bridging

The GA system is exposed via a type-safe API boundary in `service_bridge.go`:

- `toAPIStrategy()` / `toInternalStrategy()` — bidirectional conversion between
  internal `mutation.Strategy` and API-layer types, with deep-copy of `Params`
  and `DimensionScores`.
- `apiGuidanceBridge` — wraps `GuidanceProvider` for API invocation, exposing
  `EvolutionHint` and `StrategyOutcome`.
- `apiMemoryBridge` — exposes memory-query capabilities like `FindSimilar`
  through the API layer.
- `llmClientAdapter` — adapts LLM clients to a unified `Generate` interface.

The bridging layer lets external systems (REST API, MCP, etc.) interact with
the evolution subsystem through a clean API boundary without exposing internal
types.

### Trigger layer

External events (`AgentEnd`, `TaskFailed`) feed `EvolutionScheduler`, which
fires on:

- **score degradation**: recent-10-mean below total-mean by 15% triggers
- **periodic**: every 100 tasks
- **manual**

`EvolutionScheduler` then selects DreamCycle or Genome GA as the evolution path.
